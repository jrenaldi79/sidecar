# MCP App Tool Coverage Audit

## Goal

Ensure the sidecar MCP App UI has renderers for every tool that OpenCode exposes, detect drift automatically, and provide a static test harness for visual QA of all tool renderers.

## Deliverables

1. **Bug fix**: `renderers.js:62` uses `part.toolName` but the OpenCode API sends `part.tool`. Tool routing currently falls through to the generic fallback for everything. Fix so renderers are actually exercised.
2. **Static test harness**: Revive `test-harness.html` + `test-harness.js` with mock data for all 12 handled tool types plus a tool coverage panel.
3. **Tool coverage E2E test**: Integration test that queries OpenCode's `/experimental/tool/ids` endpoint and asserts our `tool-output.js` covers every tool.
4. **Gap documentation**: `docs/tool-coverage.md` listing the full coverage matrix and instructions for building missing renderers.

## Architecture

### Bug Fix: Tool Name Routing

`renderers.js:62` currently reads:
```js
const name = part.toolName || part.state?.input?.description || 'tool';
```

The OpenCode API sends `part.tool` (e.g. `"bash"`), not `part.toolName`. This means `name` resolves to `part.state?.input?.description` (e.g. `"List files in current directory"`), and `formatToolOutput(name, ...)` in `tool-output.js` can't route to the correct formatter because none of the `if (name === 'bash')` checks match a description string.

**Fix**: Inside `makeToolBlock(part)`, derive both the tool ID and display label from the `part` object (no signature change needed since it's all on `part`):
```js
const toolId = part.tool || part.toolName || '';
const displayName = part.state?.input?.description || toolId || 'tool';
```

Three lines in `makeToolBlock` change:
- **Line 62**: Replace `const name = part.toolName || ...` with the two variables above
- **Line 71**: Change `label.textContent` to use `displayName` (human-readable label for the UI)
- **Line 83**: Change `formatToolOutput(name, ...)` to `formatToolOutput(toolId, ...)` (tool ID for routing)

### Tool Coverage E2E Test

**File**: `tests/mcp-app/tool-coverage-e2e.integration.test.js`

Gated on whether the `opencode-ai` binary is available (not `OPENROUTER_API_KEY`, since this test does not make LLM calls -- it only queries the tool registry endpoint). Skip pattern:
```js
const HAS_OPENCODE = (() => { try { require.resolve('opencode-ai'); return true; } catch { return false; } })();
const describeToolCoverage = HAS_OPENCODE ? describe : describe.skip;
```

**Test flow**:
1. Start a real OpenCode server via `tests/helpers/start-server.js`
2. Query `GET http://localhost:{port}/experimental/tool/ids` to get the authoritative tool list
3. Parse `src/mcp-app/tool-output.js` source to extract all tool names from routing checks. The regex must handle compound `||` patterns (e.g. `if (name === 'question' || name === 'askuserquestion')`). Extract all quoted string operands adjacent to `name ===` across the entire file, not just single-tool lines.
4. Compare the two lists:
   - Filter out `invalid` from the OpenCode list (error sentinel, not a real tool)
   - Assert every remaining OpenCode tool ID has a matching entry in our routing table
5. On success or failure, write `tests/fixtures/tool-coverage.json` (gitignored, outside `src/` to avoid being published to npm):
   ```json
   {
     "generated": "2026-03-14T...",
     "opencode": ["bash", "read", "write", ...],
     "handled": ["bash", "read", "write", ...],
     "missing": ["websearch", "codesearch", "skill", "apply_patch"]
   }
   ```
6. The test **fails** if `missing` is non-empty, with message:
   ```
   Missing renderer for tools: websearch, codesearch, skill, apply_patch
   Add formatters in src/mcp-app/tools/ and wire them in tool-output.js.
   See docs/tool-coverage.md for instructions.
   ```

**Note**: The test will initially fail because we have 4 missing tools. We mark these as known gaps (skip assertion for documented gaps) until renderers are built. The test structure is:
- Hard assertion: no **undocumented** missing tools (new OpenCode tools we didn't know about)
- Soft warning: documented gaps listed in the coverage JSON

This means the test passes today but will fail if OpenCode adds a new tool we haven't seen before.

### Gap Documentation

**File**: `docs/tool-coverage.md`

Contents:

**Tool Coverage Matrix** -- table of all OpenCode tool IDs, whether we have a renderer, and the renderer file path.

**Missing Tool Details**:

| Tool | Description | Status |
|------|-------------|--------|
| `websearch` | Web search with query, returns search results | Known gap |
| `codesearch` | Code-aware search (semantic/symbol search) | Known gap |
| `skill` | Invoke a skill by name with arguments | Known gap |
| `apply_patch` | Apply a unified diff patch to files | Known gap |

**How to find input/output schemas**: Query `GET /experimental/tool?provider={provider}&model={model}` with a valid provider/model pair. Returns JSON schemas for each tool's parameters.

**How to build a new renderer**:
1. Query the schema endpoint to understand input/output shape
2. Start the interactive harness (`npm run dev:ui`) with a prompt that exercises the tool
3. Inspect raw API data via the browser console or CDP
4. Create `src/mcp-app/tools/<name>.js` following the existing CJS pattern (`formatXxxOutput(input, output)` returning HTML string)
5. Wire it in `tool-output.js` with an `if (name === '<name>')` check
6. Add mock data to `test-harness.js`
7. Add unit test in `tests/mcp-app/tools/<name>.test.js`
8. Remove from the known gaps list in the E2E test
9. Run `npm run qa:ui` to visually verify

**Reference**:
- OpenCode SDK types: `node_modules/@opencode-ai/sdk/dist/gen/types.gen.d.ts`
- Tool IDs endpoint: `GET /experimental/tool/ids`
- Tool schemas endpoint: `GET /experimental/tool?provider=X&model=Y`
- Existing renderer pattern: `src/mcp-app/tools/bash.js` (simplest example)
